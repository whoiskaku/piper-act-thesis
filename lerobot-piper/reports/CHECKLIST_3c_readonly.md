# ③c 只读核验步骤（**不启用运动、不修改参数、不复放**）

草案 2026-09-21。**这份清单本身不构成放行依据**，它只是把
「安全审查需要的事实」从「跑实验」里分离出来。

## ⚠ 三条边界，执行前先读

1. **本清单全程只读。** 不发 `JointCtrl`、不使能电机、不改任何固件或 SDK 参数。
   一旦需要写参数或让臂运动，**属于另一个步骤，另行申请**。
2. **读到的限速/加速度不能直接与请求差分比较。**
   必须先确认它约束的是「**下发目标的变化**」还是「**控制器内部生成的运动轨迹**」。
   若是后者，请求的二阶差分超过它**可能只意味着控制器会整形** ——
   **既不直接证明危险，也不证明安全**。
3. **得到数字 ≠ 完成安全审查。** 本清单产出的是**事实**，
   是否放行由这些事实 + 适用性判断共同决定。

## 专用脚本：`sim/readonly_check_3c.py`

**不走** `make_robot` / lerobot 的 robot 包装 —— 现有连接流程会**使能 + 标定归位**，
断开流程也可能发送动作，**不能借它来「只读」**。本脚本直接用 `piper_sdk`。

### ⚠ 准确表述：这是**护栏**，不是不可绕过的安全边界

2026-09-22 审查复现了两条绕过路径（**纯假对象，未导入 SDK、未碰 CAN**），**均已修**：

| 绕过路径 | 修法 |
|---|---|
| `p._inner.JointCtrl()` —— 内部对象存成属性，可取到后绕开代理 | 内部对象改存**闭包**，`p._inner` **不存在** |
| `p.ConnectPort()` 不传参 ⇒ `piper_init` 默认 `True`，绕过查询开关 | `ConnectPort` **移出允许清单**，改由**参数固定**的 `connect_readonly()` 入口 |

但 Python 层面不存在真正不可绕过的边界 ⇒ **只能称「护栏」**。

| 三层 | |
|---|---|
| **允许清单代理** | `__getattribute__` 层拦截；不在清单里取到即抛 `ForbiddenCall`；写/删属性一律拒绝 |
| **`connect_readonly()`** | **参数固定** `piper_init=False`；默认 `True` 会自动调 `PiperInit()` |
| **两道确认** | `--i-confirm-arm-is-idle` + `--send-query-frames`，都不给就不连接设备 |

### ⚠ 查询也是往总线写帧 —— **共 13 帧，不是 3 帧**

`PiperInit()` = `SearchAllMotorMaxAngleSpd`(**6**) + `SearchAllMotorMaxAccLimit`(**6**)
+ `SearchPiperFirmwareVersion`(**1**) = **13 帧**。
它们**不是运动指令，但确实是总线写入** ⇒ 默认**不发**。
要读**固件侧**（应答式）的限位/限速/加速度/固件版本才需要 `--send-query-frames`。

### ⚠ `DisconnectPort()`：不发动作成立，但**不能声称线程已全部退出**

源码核实：它只置标志、设停止事件、关 CAN 口，**不发任何动作**。但

- SDK 建了 `__can_deal_th` 与 `__can_monitor_th` **两个**线程；
- `can_monitor_th` 的 join **被注释掉**；
- `can_deal_th` 的 join 守卫写的是 `hasattr(self, 'can_deal_th')`，
  与名字改写后的真实属性 `_C_PiperInterface_V2__can_deal_th` **不匹配**
  ⇒ **该 join 分支实际从不执行**。

### ⚠ 六关节完整性：按**接口结构**查，不靠递归搜同名字段

按实物核对 SDK 结构后修了三处误判（旧版会**漏判**也会**误判**）：

| 实物结构 | 旧版的错 |
|---|---|
| `motor` 是**长度 7** 的列表，**`motor[0]` 是占位** | 六关节全回复时得到 `[0,1,…,6]`，反而判「不完整」 |
| 加速度用 **`joint_motor_num`**，不是 `motor_num` | 提取不到任何编号 ⇒ **跳过检查**；只有 j1 回复也被标 `valid` |
| 对象里还有名字改写的私有副本 `_Arm…__m`，与 `motor` **内容重复** | 递归搜同名字段会**重复计数** |

现在：**只对两个聚合接口**（`GetAllMotorAngleLimitMaxSpd` / `GetAllMotorMaxAccLimit`）
做检查，定位**公开的** `motor` 列表后**逐槽**确认 `motor[i]` 的编号 `== i`（i=1…6）
且数值非零；单电机 `GetCurrent…` 返回值**不套用**这个检查。

### ⚠ 静止确认：分开比较，且必须**正向**推进

旧版 `moved = j0 != j1` 比的是**完整快照（含时间戳）** ⇒
只要时间戳推进 `moved` 必为真 ⇒ **`confirmed_idle` 永远不成立**。
现在：

- 比关节角前**剥掉 `time_stamp` / `Hz` 等元数据**（`strip_meta`）
- 时间戳必须**正向推进**（`advanced`）：**倒退判 False**，不动也判 False
- `confirmed_idle` = 正向推进（证明在收流）**且** 关节角不变

### ⚠ 查询证据：与普通状态流**分开**

`GetArmStatus` / `GetArmJointMsgs` 是**持续更新的状态流**，
**没发查询也会推进** ⇒ **不能**用来证明查询已发送或得到回复。现在分三项记录：

| 字段 | 内容 |
|---|---|
| `query_evidence.authorized` | 查询是否获准（开关） |
| `query_evidence.methods_called` | 实际调用了哪些查询方法 |
| `query_evidence.responses` | **只看应答式接口**：回复是否收到（正向推进）+ 六关节是否完整 |
| `query_evidence.send_layer_evidence` | **`null`** —— SDK 不回报逐帧发送结果 ⇒ **无发送层证据** |
| `status_stream` | 普通状态流**单独报告**，仅用于判断是否在收流 |

`steps_done` 的措辞改为「**已尝试调用三组查询（无发送层证据，不保证 13 帧全部发送成功）**」。

### ⚠ 反馈有效性：**「没抛异常」不等于「读到了」**

每项读取都标 `status`：`valid` / `no_reply` / `stale` / `error` / `unknown`。

- 固件读不到时返回 **`-0x4AF`** ⇒ 判 `no_reply`（不是成功）
- `time_stamp` 全为 0 ⇒ `no_reply`；两次读取**未正向推进**（含倒退）⇒ `stale`
- 应答式的六电机数据按**接口结构**逐槽查完整性（见上），缺项即降级
- **连接标记为真不证明收到了设备反馈**
- **静止确认必须「`time_stamp` 推进（证明在收流）**且**读数不变」**；
  断流时两份相同缓存**不算**静止确认
- `query_frames_sent_evidence` = **查询前后 `time_stamp` 是否推进**，不是开关值

### ⚠ 两处接口订正

- `GetArmModeCtrl` 返回的是**监听到的 0x151 控制命令缓存**，
  **不是设备当前模式反馈** ⇒ 当前模式看 **`GetArmStatus`（CAN 0x2A1）**。
- `GetSDKJointLimitParam(joint_name)` **必须传关节名** ⇒ 逐个读 `j1…j6`。

### 记录

- `dump()` **递归**展开 list/dict/tuple（否则六电机列表被压成字符串）
- CAN 接口状态按 `--can` 记录（不再固定 `can0`）
- **每次运行独立文件** `outputs/probe_3c/readonly/readonly_<UTC>[_q].json`，不覆盖
- 连接/查询异常时**已完成步骤与异常一并落盘**（`steps_done` / `fatal`）

### 三步执行

```
# ① 离线自检（**不碰 CAN**）—— 审查用这个，已跑通 7/7
python -u sim/readonly_check_3c.py --dry-run

# ② 现场确认机械臂静止、无其他程序发指令后（**不要切换电机状态**）
python -u sim/readonly_check_3c.py --i-confirm-arm-is-idle

# ③ 需要固件侧限值时，额外显式同意发查询帧
python -u sim/readonly_check_3c.py --i-confirm-arm-is-idle --send-query-frames
```

离线自检 **24 项全过**（对齐真实 SDK 结构离线构造）：允许清单 · 19 个禁用方法全拦 ·
**两条绕过路径已堵** · 写删属性被拒 · 查询帧需显式开启且开启后动作仍被拦 ·
`-0x4AF` / 全零时间戳判定 · `dump()` 递归 · **跳过私有副本避免重复计数** ·
**含 0 号占位的完整六关节判 complete** · **加速度只回 j1 判不完整** ·
**新鲜反馈+关节不变判静止** · **时间戳倒退不判推进** ·
**不发查询但状态流更新不算查询成功** · 未导入 lerobot robot 包装。

⚠ **自检只覆盖代理与判定逻辑**；真实接口的反馈内容仍须上机后按 `status` 字段逐项核对。

## 已知的、本清单不解决的

- `piper.py::write` 的 docstring 位置范围**与实机不符**：
  裸 `u` 的 j2 实到 106166（0.001°）而文档写 90000，且该轨迹已跑过 40+ 集。
  ⇒ **文档陈旧**是一种解释，但「跑过 40 集」是**经验依据**，
  **不足以单独证明文档错误或安全边界成立**。R3 的厂商侧位置限位可以澄清这一条。
- `piper.py::write` 发送路径**无软件速度/加速度限幅**（只做单位转换、取整、发送）。
  **不能假定 G 的限幅器在这里兜底** —— G-v2 的 `A_MAX` 是阶跃拟合的**模型参数**，
  且**裸 ACT 轨迹本身就超它最多 7.6×**。
